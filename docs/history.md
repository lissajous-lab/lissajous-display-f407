# 资料整理说明

赛后整理仓库时，手上其实有两套东西。这里说清楚**什么进了仓库、什么没进、为什么**，
免得以后自己或队友找不到某份材料时又去翻硬盘。

## 2. 为什么只收最终版代码

仓库里是**一份能编译、能烧录、能跑**的工程，不是版本收藏夹。

16 个 K230 迭代版本全部塞进来，会让仓库多出 1 MB 无用代码，
而真正有价值的信息只是「每个版本解决了什么问题」——那张表放进了 `K230/README.md`。

同理，`原档` 与 `FFT_20` 两套同源工程只保留一套。Git 本身就是版本管理工具，
把「改之前的样子」也塞进同一棵目录树里，等于用文件夹做 Git 该做的事。

> 需要历史版本时，用 Git 自己：
> `git log --oneline` 看提交，`git show <commit>:Core/Src/main.c` 看当时的内容。

## 3. 为什么没收录「锁相环」那个工程

那份是赛前练手的 F103 工程（AD9833 + OLED + 卡尔曼滤波），和最终方案有三处根本不同：

| 项 | 练手工程 | 最终方案 |
|---|---|---|
| 主控 | STM32F103 | STM32F407 |
| 库 | 标准外设库 | HAL + CubeMX |
| DDS | AD9833（无相位寄存器输出） | AD9834 |
| 测相 | 卡尔曼滤波估计 | 双 ADC 同步采样 + 正交投影 |

它证明的是「赛前把基础打了一遍」，不是本装置的实现。混进同一个仓库，
读代码的人会分不清哪份是参赛代码。

## 4. 仓库现在的信息层次

| 想了解什么 | 看哪里 |
|---|---|
| 这东西干什么、指标多少 | `README.md` |
| 题目要求、每条落在哪段代码 | `docs/problem.md` |
| 用了哪些硬件、为什么这么接 | `docs/hardware.md` |
| 第五题两块板怎么通信 | `docs/vision-protocol.md` |
| 每段代码的职责与坑 | `README.md` 第 5、8 节 + 各头文件注释 |
| 想改代码要守什么规矩 | `CONTRIBUTING.md` |
| 照片视频放哪 | `docs/media.md` |
| 为什么没有某份材料 | 就是本文件 |

核心原则：**代码给实现，文档给理由**。代码里能看出来的事情文档不重复，
文档只写代码里看不出来的——为什么这么选、踩过什么坑、换器件要改哪里。
