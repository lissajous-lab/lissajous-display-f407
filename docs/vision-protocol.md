# 第五题：STM32 ↔ K230 串口协议

第五题是「摄像头拍示波器屏幕 → 自动把图形调出来」。主控和视觉子机之间只有一条 UART，
本文把这个协议写清楚——仓库里没有第二份文档讲它，读代码容易漏掉重发机制和限幅。

| 项 | 内容 |
|---|---|
| 物理连接 | STM32 `PB10/USART3_TX` → K230 `RX`；`PB11/USART3_RX` ← K230 `TX`；共地 |
| 参数 | 115200，8 位，无校验，1 停止位 |
| K230 侧引脚 | UART3，TX = GPIO50，RX = GPIO51（`main.py` 第 68~73 行） |
| 协议版本 | STM32 侧 `F5_FFT_OU_SLAVE_1.4_NO_TIMEOUT`；K230 侧 `F5_VISUAL_PLL_6.1_Q3_DOUBLE_THEN_SWEEP` |

双方只在**进入视觉模式时**才建立这条链路。正常模式（前四题）下 USART3 不初始化。

---

## 1. 帧格式

纯 ASCII 行，`\r\n` 结尾，`$` 开头，逗号分隔：

```text
$命令,参数1,参数2,...\r\n
```

接收端按 `\n` 切行，忽略 `\r`；单行上限 128 字节（`VISION_LINE_SIZE`）。

两个由实现决定、必须守住的细节：

- **命令名区分大小写**。匹配用的是逐字符比较（`VisionSlave_Equals`），`SET` 与 `set`
  不是一条命令，发小写会走到未知命令分支、回 `ERROR`。
- **超长行不是整行丢弃，而是会被截成尾部片段**。缓冲写满 127 字节后长度清零，
  后续字节从行首重新累计，到 `\n` 时这段尾巴仍会被当成一条命令解析。
  发送端务必把行控制在 100 字节以内。

选 ASCII 而不是二进制，是为了**能用任意串口助手直接看到收发内容**。
比赛现场调试时这一条省了大量时间。

## 2. STM32 → K230

| 消息 | 含义 | 何时发 |
|---|---|---|
| `$MODE,VISION` | 进入视觉模式 | 按 PA0 切入第五题 |
| `$MODE,NORMAL` | 告知已离开视觉模式 | 由 `VisionSlave_DeInit()` 发出；**当前固件没有调用点**（见 4.3） |
| `$STM32_READY,<版本>` | 主控就绪，并声明协议版本 | 进模式时、收到 `K230_READY` 时 |
| `$START,LINE` | 启动第 1 小问（斜线） | 按 PD12 |
| `$START,CIRCLE` | 启动第 2 小问（圆/椭圆） | 按 PD13 |
| `$START,INFINITY` | 启动第 3 小问（倒 8） | 按 PD3 |
| `$APPLIED,<seq>,<probe>` | **命令已执行** | 每次成功写 DDS 后 |
| `$ERROR,<seq>,<probe>,<原因>` | 命令被拒绝 | 参数非法 / 写 DDS 失败 / 未在运行 |

`seq`（序号）和 `probe`（探测号）由 K230 生成，STM32 原样回显——这是配对依据。

## 3. K230 → STM32

### 3.1 控制类（需要应答）

| 消息 | 含义 |
|---|---|
| `$SET,seq,probe,freq_mHz,phase_mdeg,ramp_wps` | 一次性写频率 + 相位 + 斜坡 |
| `$FREQ,seq,probe,freq_mHz` | 只改频率（最常用） |
| `$PHASE,seq,probe,phase_mdeg` | 只改相位 |
| `$RAMP,seq,probe,ramp_wps` | 设置频率斜坡速度（每秒钟多少频率字） |

单位全部是**毫单位整数**：`freq_mHz` 是毫赫兹，`phase_mdeg` 是毫度。
例如 10 kHz 发 `10000000`，90° 发 `90000`。用整数是为了和主控内部的定点实现对齐，
避免浮点在两颗芯片上舍入不一致。

### 3.2 状态类（不需应答）

| 消息 | 含义 |
|---|---|
| `$K230_READY,<版本>` | 视觉端就绪，请求进入视觉模式 |
| `$RUNNING,<图形>,<版本>` | 某一小问开始扫描 |
| `$LOCKED,<图形>,<输入频率>,<锁定耗时ms>` | 已锁住，仍在保持 |
| `$DONE,<图形>,<输入频率>` | 该小问完成 |
| `$FAIL,<图形>,<原因>` | 失败，冻结相位运动 |

`<图形>` 取 `LINE` / `CIRCLE` / `INFINITY`。

## 4. 时序

### 4.1 握手

```text
K230                          STM32
  |  $K230_READY,6.1...   →   |
  |                          ←  |  $MODE,VISION
  |                          ←  |  $STM32_READY,F5_FFT_OU_SLAVE_1.4...
  |  （此后才允许下 $SET/$FREQ）  |
```

两边都做了容错：

- STM32 收到 `HELLO` 或 `K230_READY` 都会回一整套握手，所以**谁先上电都行**。
- K230 收到 `START` 也会把 `vision_enabled` 置真——即使 `MODE` 那一帧在复位时丢了，
  按键依然能启动。这个兜底是现场调试出来的：两块板同时复位时 `MODE` 丢过好几次。

### 4.2 命令-应答

K230 每发一条控制命令就等应答：

| 参数 | 值 | 位置 |
|---|---|---|
| 单条命令超时 | 1200 ms | `main.py` `UART_ACK_TIMEOUT_MS` |
| 重试次数 | 3 | `main.py` `UART_COMMAND_RETRIES` |
| 重试间隔 | 20 ms | — |

配对规则：`APPLIED` 的 `seq` 与 `probe` **同时**匹配才算这条命令成功。
只匹配 `seq` 不够——斜坡扫描时同一 `seq` 会连续发多条，`probe` 才是区分依据。

超时重发的前提是**命令幂等**：重复写同一个频率结果相同，所以重发安全。
这也是为什么协议里没有「相对增减频率」这种非幂等命令。

### 4.3 无应答超时的设计取舍

STM32 侧协议版本里的 `NO_TIMEOUT` 指的是：**主控不主动超时清理会话**。
它只管收命令、执行、回 `APPLIED`。谁发起、什么时候放弃，全由 K230 决定。

好处是主控逻辑极简，不会出现「主控已经放弃但 K230 还在等」的僵局；
代价是如果 K230 挂了，主控会一直停在视觉模式等下去。

**而且视觉模式是单向的**：`app_mode` 在 `AppMode_EnterVision()` 里置成 `APP_MODE_VISION` 后，
主循环再没有把它改回 `APP_MODE_NORMAL` 的路径，PA0 在视觉模式下也不参与轮询。
所以进第五题后要回前四题，只能复位或重新上电。这是比赛现场的取舍——宁可不能软切换，
也不要在计时中途误按 PA0 掉回正常模式。`VisionSlave_DeInit()` 会发 `$MODE,NORMAL`，
但它当前没有调用点，留着是为了将来接回退逻辑时协议不用改。

## 5. 频率范围与限幅

不同小问的扫描范围不同，超范围直接回 `$ERROR`：

| 小问 | 按键 | 允许范围（毫赫兹） | 折算 |
|---|---|---|---|
| 斜线 LINE | PD12 | 1,000,000 ~ 100,000,000 | 1 kHz ~ 100 kHz |
| 圆 CIRCLE | PD13 | 1,000,000 ~ 100,000,000 | 1 kHz ~ 100 kHz |
| 倒 8 INFINITY | PD3 | 2,000,000 ~ 200,000,000 | 2 kHz ~ 200 kHz |

倒 8 要 2 倍频，所以上限放到 200 kHz——输入 100 kHz 时输出 200 kHz，正好卡满。

斜坡 `ramp_wps` 限幅 ±8192（`VISION_RAMP_LIMIT_WPS`），单位是「频率字/秒」。
按 75 MHz 主时钟、28 位频率字算，8192 字/秒 ≈ 2.3 kHz/秒 的扫描速度。

## 6. 错误码

| 原因 | 触发条件 |
|---|---|
| `BAD_SET` / `BAD_FREQ` / `BAD_PHASE` / `BAD_RAMP` | 字段解析失败（非数字、溢出、参数个数不对） |
| `NOT_RUNNING` | 没按启动键就下命令 |
| `DDS_SET` / `DDS_FREQ` / `DDS_PHASE` | 写 AD9834 时 HAL 返回错误 |
| `BAD_SHAPE` | （K230 侧）图形名不在三类里 |

收到任何 `$ERROR`，K230 立刻抛异常并终止该小问，不会带着错误状态继续扫。

**一处例外**：`BAD_*` 这类解析失败回的是 `$ERROR,0,0,<原因>`，不是原样的 `seq/probe`——
字段都没解析出来，主控拿不到可信的序号，硬回填反而会让 K230 把错误配到别的命令上。
K230 侧靠命令超时兜底，收到 `seq=0` 的 `ERROR` 直接判本小问失败。

## 7. 视觉判据（K230 侧）

识别阈值都在 `main.py` 开头，改之前先看这里：

| 常量 | 值 | 判据 |
|---|---|---|
| `LINE_AXIS_RATIO_MAX` | 0.45 | 长短轴比 ≤ 0.45 判为斜线 |
| `CIRCLE_AXIS_RATIO_MIN` | 0.84 | 长短轴比 ≥ 0.84 判为圆 |
| `CIRCLE_PHASE_MIN_DEG` | 80.0 | 相位差 ≥ 80° 才算正交 |
| `CIRCLE_ELLIPSE_ERROR_MAX` | 0.23 | 椭圆拟合残差上限 |
| `INFINITY_AXIS_RATIO_MIN` | 0.94 | 倒 8 要求更「方」 |
| `INFINITY_SYMMETRY_MAX` | 0.15 | 上下左右对称性误差 |
| `INFINITY_CENTER_MIN/MAX` | 0.045 / 0.14 | 中心凹陷位置（倒 8 的腰部） |
| `INFINITY_HORIZONTAL_CROSSINGS_MIN` | 3 | 水平穿越次数下限 |
| `LOCK_DEADLINE_MS` | 60000 | 单小问最长 60 秒，超时判失败 |

倒 8 与斜线都用「长短轴比」，但阈值几乎互补（0.45 vs 0.94），
中间留出的 0.45~0.94 是「还没调好」的过渡区，两边都不认——避免半成型图形被误判完成。

## 8. 怎么调试这条链路

1. **先只看单向**：USB-TTL 接 K230 的 TX，串口助手看 `$K230_READY` 有没有出来。
2. **再看握手**：STM32 进视觉模式后应回 `$MODE,VISION` 与 `$STM32_READY,<版本>`。
   **版本号必须两边都打印**，否则至少有一块板还在跑旧程序——这是踩过的坑。
3. **单条命令验证**：串口助手手动发 `$FREQ,1,1,10000000\r\n`，
   应收到 `$APPLIED,1,1`，同时示波器上频率变成 10 kHz。
4. **看重发**：如果串口上反复出现同一 `seq`，说明应答没回来——
   先查共地，再查 `$APPLIED` 里的 `probe` 是否和发出的一致。

## 9. 早期版本的协议（已废弃）

赛前第一次联调用的是 5 字节二进制帧：

```text
0x2C 0x12 <y> <c> 0x5B
```

固定帧头帧尾、单字节数据。优点是极省带宽，缺点是**没法带序号、没法带单位、没法扩展**，
一旦丢帧只能整段重来，也没法在串口助手里直接读懂。

改成现在的 ASCII 行协议后，代价是每条约 30 字节（115200 下约 2.6 ms），
换来的是可读、可扩展、可重发。这个交换在联调阶段非常值。
